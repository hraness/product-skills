# Maintain product packages

Use Node.js 24. `npm run reconcile` reads the public Hraness product directory and
the selected products' `/integrations/PRODUCT.json` bundles. It checks changed
inputs against each product's installation and selected-file requirements.
Run `npm run check` and review the resulting pull request before merging it.

Yaptake is checked against its admitted release record and Sparkle appcast,
including version, build, platform, archive address, checksum and signature
consistency. Sponge is checked against the exact public npm version, executable
and archive integrity. A source that refers to an unpublished runtime waits;
the previous admitted package is preserved. These checks do not run the native
app, inspect a private library or establish live host compatibility.

Textmock includes one Node.js helper for creating editable conversation links.
Its version belongs to that helper, independently of the web editor's updates.
The public helper download must match the selected bundle bytes. The renderer
also places it inside each skill directory so standalone skill installers include
it. Downloaded code is compared as text; these checks do not execute it.

Dawn's skill and original score example require an installed private preview.
The public bundle states that access requirement and the release version selected
by Dawn's exporter. Its source check reads the public setup and agent guides; it
does not fetch, publish or verify the private application release. The catalog
records this scope as `selected-files-only`.

The source bundle owns the skill, product README and MIT license. The renderer
copies them unchanged into a standalone product plugin and the root skill
directory. Portable Agent Plugins metadata and Claude, Cursor and OpenAI
overlays refer to the same files. The local command must already be installed.
MCP configuration is included only when the product declares that interface.

## Check and package a change

```sh
npm run check
npm run package
```

The package command writes one deterministic ZIP per admitted plugin, a
`SHA256SUMS` file and a release plan under `dist/`. Each plugin has its own
monotonically increasing integration version. Its `runtime.json` keeps the
separate app or CLI release requirement. A workflow change alone does not
pretend that the product runtime has changed.

Each product stores a fingerprint of its selected source and rendered ZIP. The
renderer computes it with fixed integration version and fingerprint values, so
those derived fields do not change their own hash. Reconciliation advances that
product's plugin revision once when the source, generated metadata or ZIP bytes
change, including an HTTP 304 source response. Changes to a public product
summary affect only that product's package. Package and check commands reject
stale fingerprints until that refresh is complete.

The release tag also includes the shared tool, action and check-source hash.
A helper-only correction can therefore receive an immutable release without
changing a product's plugin version. Identical product archives retain their
first verified publication record.

Shared tools also have a SemVer release for action consumers. The major and minor
come from `package.json`; the patch is the first-parent commit count of the
checked main candidate. The publisher fetches complete history from only
`refs/heads/main` and counts that candidate SHA. A changed tool-source hash creates
an immutable `vMAJOR.MINOR.COUNT` release with `toolkit.json` and `SHA256SUMS`.
An unchanged hash reuses its verified release. The first tooling release does not
require a product package, and tooling-only releases add no product publication
record. Do not bump a version by hand for routine tool changes.

`reconcile-report.json` reports `updated`, `unchanged` or `pending` for each
selected source. Conditional requests use the last admitted ETag. An unchanged
bundle keeps its plugin version and generated bytes. A pending source is not
removed or substituted with an unqualified one.

## Follow automated updates

The scheduled reconcile workflow uses the dedicated `hraness-distribution`
GitHub App to push an update branch and open a protected pull request. Configure
the repository variable `DISTRIBUTION_APP_ID` and secret
`DISTRIBUTION_APP_PRIVATE_KEY`. Trusted-main refresh and delivery jobs mint a
short-lived token for this repository only, with contents, pull-request and
Actions write permissions. They verify the App ID, slug, Hraness owner and
one-repository installation scope before source writes. Missing setup stops the
update; it never falls back to the built-in repository token.

App-created pull requests, branch updates and merges trigger ordinary CI. The
current head must pass `Required` before a protected merge. The built-in
`GITHUB_TOKEN` is used separately for read-only check inspection, owned issue
reports and release publication. It cannot create unattended pull requests:
[GitHub requires approval for those workflow-created PR runs](https://docs.github.com/en/actions/concepts/security/github_token).
An explicit repair dispatch is allowed only when both the exact-head check and
the canonical workflow run are absent. A waiting or approval-held run stays held.

An open owned update is refreshed with the latest generated files after its head
has been reconciled with current main. The refresh changes only the allowed
package or ledger files and refuses a concurrent branch writer. It keeps pending
verified publication entries and their first timestamp when adding later records.
A proposal whose desired files already match main closes without another merge.

The main-branch check remains separate from the pull-request check. Publication
uses the successful main commit, verifies the repository is public and packages
only admitted products. The release stays a draft until its archives and
checksums have been uploaded. An immutable public release readback must confirm
the asset digests before it can enter `publication-ledger.json`.

The publisher finds drafts through the authenticated release list and reads the
selected release by numeric ID. GitHub's published-tag endpoint can return 404
while that draft exists. A matching draft resumes with its existing assets;
conflicting sources, duplicate versions or different bytes stop publication.
After an interrupted create, upload or publish request, the publisher reads the
same object before deciding whether the operation completed. It preserves
existing releases and assets.

Automation failures report the command, step, error type and HTTP status when
available. They omit command arguments, credentials and provider response text.
Workflow changes also need an Actions schema check: plain YAML and cost checks
do not catch expression-context errors. The regression tests cover status
functions inside environment values; use `job.status` there and status functions
in the job or step condition.

The release ledger update also travels through an App-owned protected pull
request and ordinary CI. Its entries are append-only and use the actual API
publication time. Store submissions and planned launches belong in
`catalog/store-status.json`, not in that ledger. An approval or listing must be
verified before a store publication can be recorded.

The publisher also checks the [official MCP Registry](https://registry.modelcontextprotocol.io/docs)
daily and after a successful main check. It reads every page for the fixed
`io.github.hraness/sponge` server, then verifies a new active listing against
that version's public npm manifest. The package's generated `mcp` fields supply
the local command, arguments and guide URL. The observer sends no credentials,
downloads no app code and cannot publish to the registry.

An observation records the registry's first publication time and the SHA-256 of
its server JSON with object keys sorted. The listing name and version determine
one permanent ledger ID. Changed metadata or publication times conflict with that ID. Deleted
and deprecated versions add no record; earlier publication records stay in the
ledger. A failed or incomplete read preserves those records and fails the
workflow visibly. GitHub publications verified in the same run can still be
proposed while registry observation is pending.

`node scripts/distribution.mjs record-registry` performs the read-only provider
check and prepares the local ledger update. Its report under `dist/` is a run
diagnostic; the protected Git commit is the durable publication history. The
observer uses the registry's [public API schema](https://registry.modelcontextprotocol.io/openapi.json),
including `include_deleted=true` when checking a version. A successful empty
result records no publication.

Dependabot action updates use the same trusted-main delivery job. It verifies
the Dependabot author, repository, exact head, canonical check workflow and
latest `Required` result. Only modifications to existing SHA-pinned `uses:` lines
are eligible; changing an action's identity or other workflow code stops the
automatic merge. A behind branch is updated conditionally and waits for its new
ordinary checks. No workflow approval or branch protection is bypassed.

## Update shared writing guides

The daily `Refresh shared writing guides` workflow copies six guides from one
public `hraness/.github` main commit. It verifies each regular Git blob before
changing the checkout. `catalog/guide-source.json` records that commit and each
file's byte count and SHA-256. Unrelated upstream commits produce no update.

Put local guide rules under a `## Repository additions` heading at the end of the
file. Synchronization preserves that section byte for byte, including its
formatting. A heading inside a fenced example does not start the section.
`npm run check` verifies the recorded shared prefix while allowing local
additions to change. Keep repository-specific contribution and agent
instructions in `CONTRIBUTING.md` and `AGENTS.md`; this workflow updates neither.

`node scripts/guides.mjs refresh` prepares the same local update. Source failures
stop before any guide is changed. The App proposes only the six selected guides
and their source record, then uses the ordinary check and protected merge path.
An open proposal receives current shared text and current main's local additions
through the same conditional branch refresh as product updates.

## Deliver action updates in another repository

`actions/deliver-dependabot` accepts the caller's numeric `repository-id`,
`owner-id`, expected `visibility` (`public` or `private`) and `check-workflow`
filename. It derives the repository name from the running workflow and checks
those facts against GitHub before writing. The dedicated App installation token
must select only that repository. Pass its ID and private key using the same
distribution variable and secret as the profile action.

Call it from trusted default-main `workflow_run` delivery after the caller's
ordinary pull-request check succeeds. Give the built-in job token `contents:
read` and `checks: read`; the action mints its separate App write token. Main
must have an effective pull-request rule and a strict `Required` status rule
bound to GitHub Actions. The action checks the canonical workflow execution,
Dependabot's bot identity, the current PR head and the complete pin-only diff.
A branch behind current main is updated with an expected-head condition and
waits for ordinary new checks. Waiting or approval-held checks receive no
replacement dispatch. Protected merging uses the checked head and no
administrator bypass.

Pin the action to the source SHA of the verified immutable tooling release that
contains it, with that SemVer tag in the comment. Include the caller's workflow
directory in weekly grouped GitHub Actions Dependabot updates. This repository
also tracks the composite action's own pinned dependencies. Verify the caller's
actual PR, branch-refresh and main-check event flow after setup.

## Prepare a directory submission

Use the product's standalone ZIP and its README as the starting point. Test a
clean install in the intended host and complete the main product task. A source
or archive check does not establish that a host can launch the local runtime.
Record those results in the delivery evidence before claiming compatibility.

- [Agent Plugins 1.0.0](https://agent-plugins.org/specification) defines the portable manifest and local MCP configuration.
- [OpenAI packaging](https://developers.openai.com/plugins/build/plugins) defines the OpenAI metadata and repo marketplace. [Desktop submissions](https://developers.openai.com/plugins/deploy/desktop-only) require eligibility confirmation for local MCP packages.
- [Claude publishing](https://claude.com/docs/directory/publish) uses a plugin bundle submission and checks each version.
- [Cursor submissions](https://cursor.com/docs/reference/plugins#submitting-a-plugin) use a public source repository and review.
- [skills.sh listing](https://www.skills.sh/docs/faq) follows actual public installations; a GitHub package alone does not establish a registry audience.

The repository does not grant store approval. Packages remain ready for review
until their actual publication is verified. Test the configured automation and
host integrations after setup; a fixture result does not establish that the live
workflow or host works.

## Keep GitHub profile links current

`actions/check-profile` validates the checked-out profile README against the
current public portfolio. It needs no App credentials, mints no App token and
changes no file. Use it after the caller's checkout in a read-only check workflow,
with the same verified tooling source pin as the synchronization action. It
checks the generated section and leaves introductions, personal links and other
text outside the markers alone. The action runs the shared `check` command
against the caller's checkout and `GITHUB_REPOSITORY` identity.

`actions/sync-profile` is a composite action loaded from its own pinned source.
It supports exactly `hraness/.github` → `profile/README.md` and
`0thernet/0thernet` → `README.md`. Each target needs one ordered, own-line pair
of `<!-- hraness-products:start -->` and `<!-- hraness-products:end -->` markers.
The action preserves every byte outside them and reads the four product facts
from `https://hraness.com/portfolio.json`. Newly introduced destinations must
answer before it proposes a README change.

The caller pins the action to the source SHA of its verified immutable SemVer
tooling release and adds the version comment, such as `# v0.1.COUNT`. Weekly
Dependabot updates advance that pin. A comment on an untagged SHA does not
establish an update path; publish the tooling version first.

Pass `app-id` from `vars.DISTRIBUTION_APP_ID` and `app-private-key` from
`secrets.DISTRIBUTION_APP_PRIVATE_KEY`. The caller's built-in token needs
`contents: read` and `checks: read`; the action mints its separate installation
token for the one authorized profile repository. Run `refresh` only on trusted
main while it remains the repository's default branch, through a schedule or
manual dispatch. The `check-workflow` input defaults
to `check.yml`; the organization profile uses its existing `ci.yml`.

Wire the caller's successful check `workflow_run` event to the same pinned
action with `mode: deliver`. Include both `automation/profile-` and
`dependabot/github_actions/` branches, and use the caller's actual check workflow
name (`CI` for the organization profile, `Check` for the personal profile).
It verifies the App bot branch, repository, exact head,
README-only diff and `Required` result before using the protected merge path.
App merges trigger ordinary main checks. Replaying delivery after a completed PR
is harmless. Callers keep their schedule, required check and weekly Dependabot
configuration; the shared code keeps the update and merge behavior in one place.
Verify the actual event flow after setup before claiming unattended operation.
